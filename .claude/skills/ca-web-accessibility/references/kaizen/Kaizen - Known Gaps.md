# Kaizen — Known Accessibility Gaps

Confirmed accessibility gaps in Kaizen components. axe won't flag most of them. Apply the consumer-level mitigation whenever you use the affected component. Track upstream status before assuming a gap is closed.

Severity uses the scale in `SKILL.md`; **axe** = would automated axe catch it.

| # | Component / file | Gap | Severity | axe | Ticket | Mitigation (consumer side) |
|---|---|---|---|---|---|---|
| 1 | `Modal/GenericModal/GenericModal.tsx` (+ `ModalAccessibleLabel`) | **`<ModalAccessibleLabel>` is a mandatory consumer step.** `aria-labelledby` points at a `useId()` id that only `ModalAccessibleLabel` renders, and `GenericModal` uses `autoFocus={false}` + `focusOnAccessibleLabel()` to move focus onto that element on open. Omit it and the dialog is **unnamed** *and* **focus never enters**. Only a `console.warn` flags it. | Critical | Partial | none | Always render `<ModalAccessibleLabel>` inside the modal. When auditing, a modal without it is a Critical finding — do not assume the dialog is labelled/focus-managed. |
| 2 | `Modal/GenericModal/GenericModal.tsx:133` | **`focusLockDisabled` is inverted.** It is forwarded as `focusLock={focusLockDisabled}` unnegated; `react-focus-on@3.10.2` defaults `focusLock` to `true`. So `focusLockDisabled={true}` **keeps the trap ON**; only `={false}` disables it. The name implies the opposite. | High | No | Kaizen ticket (see below) | Don't rely on the prop's name. To keep the trap (the safe default) omit it. Never write `focusLockDisabled={false}` expecting a no-op — it disables the trap and focus escapes the modal. |
| 3 | `Modal` (Generic/Confirmation/Context) | No `aria-modal` on the dialog; `role="dialog"` is hand-rolled on a div; focus trap is `react-focus-on`, **not** React Aria. | Medium | No | none | Don't assume React Aria dialog semantics. The trap works via `react-focus-on` (rows 1–2 are the real risks); with no `aria-modal`, some SRs won't scope to the dialog — rely on `ModalAccessibleLabel` + the trap. |
| 4 | `Modal` heading | Heading hardcoded `<h2>`. | Low | Partial | none | Keep the surrounding outline valid — modal heading is `h2`; ensure that's correct in context (Composition pattern 3). |
| 5 | `Workflow/.../ProgressStepper/ProgressStepper.tsx` (lines 59, 106) | Hardcoded `id="stepper-description"` + `aria-labelledby`; no `useId()`. Two steppers on a page = duplicate ids, broken labelling. | High | Yes | **KZN-4101** | Render at most **one** `ProgressStepper` / `Workflow` per page until fixed. |
| 6 | `RichTextEditor > LinkModal > TextField` | Hardcoded `id="href"` — dup-id risk if two link modals mount. | Medium | Yes | **KZN-4101** | Avoid two `RichTextEditor` link modals open simultaneously. |
| 7 | `ToastNotificationsList` / `KaizenProvider` | Hardcoded container `id="toast-notifications-list"` on `document.body`; dedup guard blocks a second container, so a nested provider's toasts never announce. | Medium | No | **KZN-4101** | Exactly **one** `KaizenProvider` at app root; never nest (Composition pattern 12). |
| 8 | `TitleBlock` | **Not a bug — usage note.** `title` renders the page **`<h1>`**. `sectionTitle` renders an **`<h2>`** automatically. `renderSectionTitle` is **consumer-rendered** — the consumer must render an `<h2>` themselves. | — | Partial | none | Treat TitleBlock as the page's `h1` owner: don't add a second `<h1>`, and start other headings (tiles, sections, guidance) at `h2` or below. If you pass `renderSectionTitle`, render an `<h2>` (a Kaizen `Heading tag="h2"` or a native `<h2>`) — nothing enforces this for you. |
| 9 | `GenericTile` | Defaults `titleTag="h3"`; skips a level with no `h2` ancestor. | Medium | Partial | none | Set `titleTag` explicitly to the correct level for the surrounding outline. |
| 10 | `FieldGroup` | Plain `<div>` — no group ARIA; grouped fields not announced as a group. | High | No | none | Wrap related fields in `<fieldset>` + `<legend>`; don't depend on `FieldGroup` for semantics (Composition pattern 7). |
| 11 | `FilterBar` | No landmark; does not coordinate popover open-state — two `aria-modal="true"` dialogs can open at once (`react-focus-on` overlays). | High | No | none | Add a landmark/label around the bar; coordinate so one filter popover is open at a time (Composition pattern 9). |
| 12 | `DatePicker` (inside a modal) | `react-focus-on` overlay sets `returnFocus={false}`; focus not returned to the date input when the calendar dismisses. | High | No | none | Verify/restore focus to the trigger on dismiss; prefer an inline calendar inside modals (Composition patterns 2, 10). |
| 13 | `Table > TableHeaderRowCell` `tooltipInfo` | Uses legacy `TooltipV1` (Popper), a different a11y model than RAC `Tooltip`. | Medium | No | none | Prefer attaching a RAC `Tooltip` to a `Focusable` host rather than `tooltipInfo` where keyboard/SR parity matters (Composition pattern 8). |

## General notes

- **Focus/contrast tokens.** Kaizen component focus visuals come from React Aria + component CSS. The raw `color.json` has no focus-named token, but `@kaizen/tailwind` exposes `border-focus-ring` (= `blue-600`) — use it for custom focusable UI and verify ≥ 3:1 (see Design Tokens). No contrast-semantic (primary/success/danger) named tokens exist.
- **Reduced motion is not systematised.** No global token/enforcement; handle per-component via `useMediaQueries` or a media query (see Design Tokens).
- **AGENTS.md §9** in the design system states single-component a11y is covered by the Storybook axe addon and defers all composition detail to the composition catalogue — so absence of an axe failure is **not** evidence a composition is accessible.
